[Chapter-4] PROJECT WORK
This chapter outlines the core focus of the industrial training: the development of the "PraxiaOne" platform. It defines the central healthcare problem the project aims to solve, outlines the primary objectives, and details the technical methodology and architecture used to achieve these goals.

4.1 Major Project Problem and Objectives
Today’s healthcare ecosystem is heavily bifurcated. On one side, consumer wellness platforms and wearables collect high-frequency lifestyle data but stop at surface-level insights. On the other side, clinical systems and patient portals store authoritative medical records and lab results but offer minimal interpretation and no execution support between doctor visits.
The core problem identified by Prime Equity, LLC is that prevention fails at execution, not data collection. Patients receive an abundance of data without clear direction, while healthcare providers lack continuous visibility into the patient's daily habits. Because neither system translates data into sustained preventive action, interventions often occur too late, specifically concerning chronic conditions like metabolic dysfunction (prediabetes) and autoimmune diseases.

4.2 Project Objectives
To address this execution gap, the primary objective of the project was to build PraxiaOne: a unified preventive health intelligence and execution platform. The specific technical and clinical objectives included:
Data Unification: To seamlessly aggregate fragmented data from wearables, lab results, Electronic Health Records (EHR), and self-reported signals into a single, cohesive system.
The Execution Layer: To translate raw data into weekly, actionable, and achievable plans (e.g., customized step goals, dietary adjustments) rather than just displaying static graphs.
Safe AI Reasoning: To utilize explainable, conservative Artificial Intelligence (Domain-specific models like Med42) to interpret medical data while maintaining strict safety guardrails.
Structured Escalation: To build a system that continuously monitors patient outcomes and automatically escalates cases to caregivers or telehealth professionals only when specific clinical thresholds are crossed.
Cost-Optimized Architecture: To develop a dynamic Cost Management Layer that optimizes the financial overhead of running multiple Large Language Models (LLMs) by routing queries based on task complexity and ROI scoring.

4.3 Methodology and System Architecture
The methodology for building PraxiaOne was rooted in an agile, multi-layered architectural approach, transitioning data through three distinct phases: Data → Intelligence → Execution.

4.3.1 Data Aggregation Layer
The system's foundation relies on a comprehensive integration framework. Wearable data streams, digital medical documents (MRI scans, discharge summaries), and structured lab results were processed and stored. A combination of MySQL (for user identities) and Neo4j (Graph Database) was utilized. Neo4j allowed the system to model highly complex medical relationships—such as linking a specific symptom to a lab result and a subsequent lifestyle recommendation—which traditional databases struggle to do efficiently.

Figure 4.1: PraxiaOne High-Level System Architecture (Data to Execution)

4.3.2 The Intelligence Layer (AI Health Engine)
Once data was normalized, it passed to the AI Health Engine. The methodology here relied heavily on Retrieval-Augmented Generation (RAG).
Vector Storage: Medical documents were chunked, converted into high-dimensional embeddings, and stored in Qdrant.
Model Routing: When a user queried the AI chat or a new lab result was uploaded, the Cost Management Layer evaluated the prompt. Simple conversational queries were routed to low-cost APIs, while complex medical reasoning tasks were routed to specialized clinical models (like Med42 or BlueBERT) running securely on local servers via Ollama.

4.3.3 The Execution and Recommendation Layer
Instead of merely displaying insights, the system methodology focused on generating a "Wellness Plan." The AI interpreted the collective data to deliver weekly, AI-guided actions. For example, if a user's recent lab showed slightly elevated cholesterol and their wearable detected poor sleep, the engine generated specific, personalized nudges (e.g., "Reduce late-night carbs" or "In bed by 11:30 PM").

Figure 4.2: Methodology Workflow of the AI-Based Personalized Recommendation System


4.3.4 Continuous Feedback Loop
The final step in the methodology was adaptive monitoring. PraxiaOne continuously tracked adherence to the generated wellness plans via connected wearables. If the data indicated improvement, the AI adapted the goals. If the data indicated deteriorating health metrics, the system's logic triggered the structured escalation pathway to notify clinical providers.

This chapter evaluates the outcomes of the PraxiaOne project development phase. It discusses the results achieved across various implemented modules, including user interface fidelity, database performance, AI model efficiency, and overall system deployment.

5.1 User Interface and Experience (UI/UX) Results
The primary front-end objective was to achieve a 1:1 pixel-perfect replication of the provided design screens for both web and mobile platforms.
Web Dashboard: All screens were successfully implemented using Next.js and Material UI (MUI). Most of the dynamic tabs accurately rendered the tasks that were allocated for them and the responsive layout adapted seamlessly to different screen sizes.
Mobile Application: The cross-platform mobile application successfully mirrored the web design. The integration of the AI chat interface and file upload features functioned smoothly, providing a consistent user experience across all devices.

5.2 Efficiency of the Cost Management Layer
One of the most significant technical achievements was the successful implementation of the Cost Management Layer.
Results: The Token Policy Engine effectively enforced daily and monthly budget caps. By integrating real-time pricing via web crawlers, the system successfully demonstrated intelligent model switching.
Discussion: Running complex Large Language Models (LLMs) can quickly become cost-prohibitive. The ROI scoring mechanism proved that routing simple conversational queries to low-cost models while reserving premium or local models (like Med42) for complex clinical reasoning drastically reduced operational costs without sacrificing accuracy.
5.3 Database and Data Integration Performance
The integration of multiple database architectures yielded highly positive results for handling medical data.
Results: The Neo4j Graph Database successfully mapped intricate relationships between patient symptoms, lab results, and action plans. Simultaneously, the Qdrant vector database efficiently managed high-dimensional embeddings for semantic search.
Discussion: Traditional relational databases (like MySQL) are highly efficient for user authentication but struggle with the interconnected nature of healthcare data. The hybrid approach allowed the system to perform complex medical queries significantly faster. By grounding the AI models in data retrieved from both Neo4j and Qdrant (Retrieval-Augmented Generation), the system avoided "hallucinations" and provided highly contextualized wellness plans.

5.4 Multi-Model AI Comparison and Clinical Testing
The project involved rigorous testing of various AI models to determine their suitability for healthcare.
Results: The system successfully ran comparisons between local clinical models (Med42,DeepSeek, BlueBERT via Ollama) and external APIs (Gemini).
Discussion: The testing revealed distinct advantages depending on the model used. General APIs like Gemini excelled at casual conversational formatting and speed. However, specialized clinical models like Med42 and BlueBERT demonstrated superior accuracy and safer reasoning when interpreting structured lab results and generating medical recommendations. Hosting these models locally via Ollama also ensured that sensitive patient data never left the secure server environment, fulfilling crucial privacy requirements.

6.2 Future Scope
While the current iteration of PraxiaOne successfully achieves its primary objectives for managing early metabolic risk, the platform is built with a modular architecture that supports extensive future enhancements. The potential future scope of the project includes:
Direct Wearable and IoT Integration: Expanding the data aggregation layer by building direct API integrations with major wearable ecosystems (e.g., Apple HealthKit, Google Fit, Oura). This will allow for real-time telemetry streaming rather than relying on batch data uploads, enabling instantaneous AI nudges based on live heart rate or sleep cycle data.
EHR Interoperability (FHIR Standards): Implementing Fast Healthcare Interoperability Resources (FHIR) standards to allow PraxiaOne to securely and automatically pull patient data directly from hospital Electronic Health Record (EHR) systems like Epic or Cerner, streamlining the onboarding process for clinical users.
Expansion of Clinical Use Cases: Adapting the graph database schema and fine-tuning specialized LLMs to handle other complex, underserved medical conditions beyond prediabetes, such as autoimmune-mediated diseases (e.g., Ulcerative Colitis) or cardiovascular risk management.
Predictive Cost Management: Upgrading the Cost Management Layer with machine learning algorithms that can predict LLM token usage and forecast monthly budgets based on historical user behavior, further optimizing cloud and API expenditures.
Advanced Mobile Engagement: Enhancing the Flutter mobile application with actionable push notifications and background data syncing, ensuring users receive timely behavior nudges (e.g., hydration reminders, post-meal walk alerts) directly on their lock screens to improve adherence to their AI-generated wellness plans.
